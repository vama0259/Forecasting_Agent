# M8 Read-Only Evaluation Engine — Design Spec

**Story:** GitHub #6 — Story 3: M8 Read-Only Evaluation Engine (MASE, Brier & Purged Gate)
**Implements:** ADR-011 (`docs/ARCHITECTURE.md:154`), ADR-012 (`docs/ARCHITECTURE.md:272`), Module Spec §9 (`docs/MODULE_SPECIFICATIONS.md:197`)
**Milestone:** MVP 1 — Indian Equities & Derivatives
**Depends on:** nothing. Parallel-safe with #4 (different language, zero file overlap).
**Review status:** **APPROVED — cleared for implementation planning.** Rounds 9 through 15 (dispatched and inline) each found and fixed at least one real defect; rounds 16 and 17 (inline, no dispatched subagent, per explicit user instruction) found nothing across two independent adversarial passes — the two-consecutive-`APPROVED` gate is satisfied. Next step: `gemini-plan-writer` per the project's HARD RULE, or a further independent (dispatched) review round first if the user prefers belt-and-suspenders given the volume of inline (self-conducted) review in rounds 14-17.

## Scope

This story builds **the scorer**: pure metric functions, a purged walk-forward splitter, an Indian cost model, and the pipeline that sequences them. It does **not** persist anything (Story #8 owns Postgres), does not mount itself anywhere (Story #7 owns the sandbox), and does not fetch data (Story #5). Inputs are arrays and dataclasses handed in by a caller; outputs are `EvalResult` objects.

Environment is local but treated as production: real fee schedule, real rate sources, no toy constants, no hardcoded absolute paths, no machine-specific assumptions. Everything here must run unchanged inside the Story #7 container.

## Structure

```
  fees.py              Indian cost schedule + IndianFeeSchedule.total_fee() (round 9 M16: not "data, no logic" — decision 7 requires it to compute the segment/side/date-selected charge, the story's most intricate single method)
  sortino.py           Layer 3
  walk_forward.py      Layer 4 splitter
  gate.py              Layer 4 verdict (splitter + point-in-time audit)
  pipeline.py          orchestration: L4 → L1 → L2 → L3
tests/evaluation/
  __init__.py
  conftest.py          shared synthetic series fixtures (seeded — round 1 H1)
  test_mase.py test_brier.py test_sortino.py test_fees.py
  test_walk_forward.py test_gate.py test_pipeline.py
```

`GateFailure` (round 1 M3, dead code — the gate returns a `GateVerdict`, it never raises) is cut from `errors.py`. `EvaluationError` is likewise cut (round 9 L5 — the identical argument: it appeared once, in this Structure listing, with nothing raising or catching it anywhere in the document; a base class earns its place only if something catches the base, and nothing did). `errors.py` now defines exactly `DegenerateBaselineError`, the one exception this spec actually raises and tests against. `tests/evaluation/__init__.py` is added (round 1 L1) matching the existing `tests/__init__.py` convention.

Flat module-per-metric, no class hierarchy. Each metric is a module-level pure function taking numpy arrays; `types.py` holds the only Pydantic models. The one class is `IndianFeeSchedule` (round 10 M20 — not "a frozen dataclass of rates"; per decision 6/round 9 M16 it owns `total_fee()`'s real computation, rate data is what it holds, not all it does) and `PurgedWalkForward` (holds split parameters, exposes `split()` — matching `TimeSeriesSplit`'s own shape, round 3's "drops into existing tooling" claim retracted at decision 5 as unearned — round 10 M19 caught the retraction hadn't propagated here, 80 lines above where it was made).

## Data Flow

```
EvalRequest(returns, forecasts, calls, timestamps, as_of, segment,
            position_notional, trade_side, capital)
  → Layer 4 gate FIRST
       purged walk-forward split feasible, else run-level INVALID (decision 5)
       per fold: min-train-size AND finiteness/non-constant baseline (decision 3) — degenerate folds recorded, not fatal alone
       fewer than 2 surviving folds ⇒ run-level INVALID (decision 3b)
       point-in-time audit: max(timestamps) <= as_of
     → any run-level failure ⇒ EvalResult(verdict=GateVerdict(status="INVALID", reasons=[...]), layers=[], layer_means={}) and STOP. L1–L3 never run.
  → Layer 1  MASE on returns          (optimized)
  → Layer 2  Brier + calibration      (decision quality)
  → Layer 3  cost-adjusted Sortino    (reported, never optimized)
  → EvalResult(verdict=GateVerdict(status="VALID", ...), layers=[...], layer_means={...})
```

**Round 10 (H18) found two defects in this diagram:** the `VALID` branch's literal `EvalResult(...)` call was missing the required `layer_means` field (measured: raises `ValidationError: missing`) — added above. And the `INVALID` branch typed its return as a bare `GateVerdict`, while `evaluate()`'s own signature (decision 9) returns `EvalResult` unconditionally — the diagram now shows the `INVALID` path also returning an `EvalResult`, with `layers=[]` and `layer_means={}` (empty, not omitted, since L1–L3 never ran and there is nothing to report — an omitted field would be a `ValidationError` on a required field, not an intentional "nothing here").

L1–L3 are computed **per fold** and aggregated, not once over the whole series. A single-shot score over the full history is not walk-forward validated, and reporting one would quietly undo Layer 4.

## Decisions

### 1. MASE denominator is the **training fold**, and the naive baseline therefore does not score exactly 1.0

Issue #6's acceptance criteria say "MASE on naive baseline (score = 1.0)". **Measured: it is 1.0621** (300-point Gaussian return series, seed 7, train 200 / test 100, Hyndman denominator `mean(|Δ y_train|)`). Exactly 1.0 only occurs if the denominator is computed on the *test* fold — which is both non-standard and mildly leaky, since the scale of the evaluation window then depends on the evaluation window.

**Decision: keep Hyndman's train-fold denominator; correct the acceptance criterion instead.** The test asserts `0.8 < mase(naive) < 1.3` on a random series and `mase(naive) == 1.0` only on a constructed series where train and test have identical mean absolute first difference. A test tuned to a wrong constant is worse than no test.

`m = 1` (first difference) on daily returns. Returns are already differenced prices; there is no weekly seasonality in a daily return series worth a seasonal-naive baseline, and asserting one would inflate the denominator and flatter every model.

### 2. MASE-beats-naive is a **weak** bar on returns, so the zero forecast is reported alongside it

Measured on the same series: naive scores 1.0621, and the **constant zero forecast scores 0.7588**. Predicting "tomorrow's return is zero" beats the naive persistence forecast by 29% without any skill whatsoever, because daily returns are near-zero-mean and roughly serially uncorrelated. ADR-011 chose MASE precisely to stop a skill-free forecast from scoring well — and on *returns*, naive-persistence is a weak enough baseline that the trap partially survives the fix.

**Decision: Layer 1 reports MASE against naive *and* a `zero_forecast_mase` field, both per fold.** A model beating naive but losing to zero is flagged `beats_naive=true, beats_zero=false`. Nothing is gated on it in this story — the gate stays as ADR-011 defines it — but the number is on every result so the M6/M7 loop cannot optimize into that gap unnoticed.

This is a genuine gap in ADR-011 found while specifying it, not a reinterpretation. Recorded here; an ADR amendment is proposed but **not applied** — that is a documentation change to an accepted ADR and awaits explicit approval.

### 3. Degenerate denominator raises, never returns — including the case a naive equality check misses

`mean(|Δ y_train|) == 0` for a constant training series (measured: `0.0`) — but that is not the only way this denominator degenerates. **Measured: `TimeSeriesSplit(n_splits=5, gap=4)` on 20 points yields train sizes `[1, 4, 7, 10, 13]`.** A 1-element train fold has zero diffs, so `mean(|Δ y_train|)` is `nan`, not `0.0` — `d == 0` is `False` and `DegenerateBaselineError` never fires; `nan` then propagates into the aggregate behind a bare `RuntimeWarning`, silently poisoning the exact aggregate this guard exists to protect (round 1 B3).

**Decision: `PurgedWalkForward` takes a `min_train_size` parameter (default 3 — the smallest train size for which `mean(|Δy|)` is defined over more than one diff, corrected below), and every metric function checks `not math.isfinite(denominator) or denominator == 0.0` before dividing.** Round 2 (B5) caught that the round-1 fix replaced the wrong check instead of extending it: `isfinite(0.0)` is `True`, so a constant training series — the exact case decision 3 opens with, and the one `min_train_size` alone does *not* rule out, since a constant array of any length has `mean(|Δy|) == 0.0` — sailed straight through the guard the fix was written to close. Measured, both branches:

```
1-element train:      mean|Δy| = nan   → not isfinite → caught
constant train (n=6): mean|Δy| = 0.0   → isfinite, == 0.0 → caught only by the explicit == 0.0 arm
```

Both arms are required; neither alone is sufficient. `min_train_size` is retained because it is a distinct guard against a different failure (too few points to diff meaningfully, e.g. `n=2`), not a substitute for the finiteness/zero check — a train fold can be arbitrarily long and still be constant.

**Round 3 (B8) caught that this guard lived in the wrong layer.** Placing the `isfinite`/`==0.0` check inside `mase()` means degeneracy is detected *by Layer 1*, but the Data Flow diagram and the Gate test bullet both promise "`INVALID` means L1–L3 were never called" — the two claims cannot both be true if L1 is the thing doing the detecting. **Decision, corrected: `gate.py` computes `mean(|Δy_train|)` for every candidate fold as part of Layer 4, before L1–L3 run at all** — it already holds the fold indices and `returns` from the splitter, so this is not new data, only moving an existing computation one layer up. A fold whose baseline is non-finite or exactly zero is recorded in `GateVerdict.skipped` and excluded from the fold set handed to L1–L3. **`mase.py`'s own `isfinite`/`==0.0` check is retained as defense in depth** (assertion on a precondition the gate is supposed to have already enforced, matching decision 8's stance that the package doesn't trust its own callers by convention alone) — but it should never fire in the pipeline's own call path, and a test asserting *that* (gate-filtered folds never trip the metric-level guard) replaces the round-1/2 framing that treated the metric-level check as primary.

**`min_train_size` corrected (round 2 M9):** round 1's stated default of 5 was justified as "one more than the `m=1` diff needs" — wrong arithmetic; a train array of size *n* yields *n − 1* diffs, so a size-2 train already yields one diff and a mean is defined at size 2. The floor that actually matters is **statistical, not arithmetic**: a mean of one diff is not a meaningful baseline scale. **Default is `min_train_size=3`** (two diffs, the smallest fold size where "mean" is not just "the one value"), stated as a judgment call, not derived from a hard requirement — configurable per call site, revisit against real fold sizes during implementation.

### 3b. Per-fold invalidity does not contradict the run-level gate verdict — it has its own accounting and its own threshold

Round 1 (B4) found that decision 3 invalidates a *fold* while the Layer-4 gate returns a *run-level* `GateVerdict`, with no rule connecting the two. **Decision: `GateVerdict.skipped: Sequence[FoldSkipReason]` records every dropped fold — degenerate baseline or below `min_train_size`, both detected per-fold by `gate.py` (decision 3's B8 fix; round 4 M14 cut the redundant `EvalResult.invalid_folds` mirror — a caller reads `result.verdict.skipped` directly). If fewer than 2 valid folds remain, the run itself is marked `status="INVALID"` with `reasons=["insufficient_valid_folds"]`** — a run scored on a single fold is a point estimate wearing an aggregate's clothes, and "less than 2" is a floor on what "aggregated" can mean at all, not a proportion.

**Round 2 (M8) found the originally-proposed 50% proportional threshold was close to unreachable on the path it was written for**, swept exhaustively: with `min_train_size=5` (round 1's value), the maximum drop fraction across feasible `TimeSeriesSplit` configurations was 0.40 — because train fold sizes grow roughly arithmetically, so only the earliest folds can ever fall below a fixed floor, and tight configurations raise `ValueError` (a different failure path) before the proportion could climb further. A threshold that fires on a documented failure mode's own worst measured case, and not much beyond it, is decorative. **The absolute-count floor (`< 2` valid folds) is not exposed to the same failure**: it fires whenever aggregation is genuinely impossible, regardless of how `n_splits`/`gap`/`min_train_size` interact, and needs no sweep to justify because it isn't a tuned proportion — it's the smallest number for which "per-fold aggregation" (this spec's own Data Flow framing) means anything.

Below the floor the run is `VALID` and reports on the surviving folds, with `GateVerdict.skipped` always populated so nothing is dropped invisibly.

### 4. Brier: use `sklearn.metrics.brier_score_loss`, pass `scale_by_half` explicitly, pin `scikit-learn>=1.7`

Do not hand-roll it. But the sklearn API changed underneath this: 1.9.0 exposes `scale_by_half='auto'`, and **the two settings differ by 2×** — measured on always-confident-and-wrong predictions: `auto` → `1.0`, `scale_by_half=False` → `2.0`. Issue #6's criterion ("always-100%-and-wrong = 1.0") holds only under the scaled convention. Relying on the default means a future sklearn flipping `auto` silently doubles every calibration number in the eval history.

**Decision: always pass `scale_by_half=True` explicitly — round 9 H13 caught that "pass it explicitly" without naming the value is satisfied by passing `False`, which returns `2.0` and breaks issue #6's criterion; pin `scikit-learn>=1.7` (the release that introduced the parameter, so the explicit call is a hard error on older versions rather than a `TypeError` surprise in CI).** `True`, not `"auto"` — `"auto"` happens to resolve to `1.0` on 1.9.0, but its resolution logic is itself sklearn-version-dependent, which is exactly the silent-drift risk this decision exists to close; `True` is a literal value with no resolution step to drift. Verified against 1.9.0: `scale_by_half=True` and `scale_by_half="auto"` both give `perfect → 0.0`, `always-wrong → 1.0`; `scale_by_half=False` gives `2.0`.

**Calibration curve: hand-rolled binning, not `sklearn.calibration.calibration_curve` (round 1 H2, corrected).** Measured: `calibration_curve(n_bins=10)` on 4 points returns 2 entries with **no bin index attached** — empty bins are silently dropped from the return value with no way to recover which of the 10 were empty. That directly contradicts the promise below. `brier.py` instead uses `np.digitize(confidences, bin_edges)` into 10 fixed-width bins over `[0, 1]`, then reports **all 10** bins explicitly, each with `(count, mean_predicted, mean_observed)` and `count=0` for empty ones. Zero-sample bins are reported as empty, not dropped — a dropped bin makes a model look better calibrated than it is.

**Bin-edge float precision, noted (round 14, inline — fresh ground, not a prior round's fix): `bin_edges = np.linspace(0, 1, 11)` does not produce exact decimal boundaries.** Measured: `bin_edges[3]` is `0.30000000000000004`, not `0.3` — so a confidence value of exactly `0.3` falls in bin index `2` (`[0.2, 0.3)`), not bin index `3` as "0.3 belongs to `[0.3, 0.4)`" would naively suggest. This is deterministic and does not break the all-10-bins-reported guarantee above, but it means a test fixture must assert against the *measured* bin index for a boundary confidence value, not an assumed one — a test hardcoding "0.3 → bin 3" would fail against the actual implementation. Testing section note added accordingly.

### 5. Layer 4 splitter wraps `sklearn.model_selection.TimeSeriesSplit(gap=...)`, and is honest that gap ≠ purge

Verified on 20 points, `n_splits=3, gap=2`: folds are `train[0:2] test[5:9]`, `train[0:7] test[10:14]`, `train[0:12] test[15:19]` — the embargo is real and the train set is strictly prior. That is the **embargo** half of López de Prado's scheme, for free, from a dependency already required.

**Notation, clarified (round 9 M17):** `train[a:b]` throughout this document means "first index `a` through last index `b`, inclusive" — the natural-language shorthand this spec has used since round 1 for describing `TimeSeriesSplit`'s returned index arrays. It is **not** Python slice syntax; the equivalent Python slice for `train[0:2]` (indices `0, 1, 2`) is `arr[0:3]`, not `arr[0:2]` (which would be only `0, 1`). Four rounds re-measured these exact fold boundaries and confirmed the underlying index values every time without anyone flagging that the display notation reads as a slice and isn't one — worth stating explicitly once, here, rather than silently rewriting dozens of occurrences of a notation that was never wrong about the *indices*, only ambiguous about how to type them into code.

It is **not purging**. Purging removes training samples whose *labels* overlap the test window — which only matters when a label spans multiple bars (an h-day-ahead return observed at t consumes data through t+h). Our Layer 1 label is a 1-step-ahead return, where a `gap >= h` embargo is exactly equivalent to purging.

**Decision: `PurgedWalkForward` wraps `TimeSeriesSplit` and requires an explicit `horizon` parameter, asserting `gap >= horizon`.** For `horizon=1` this is complete and correct — verified: at `gap=1` the train fold ends at index 3 and the test fold starts at index 5, no label overlap. For multi-bar labels it raises `NotImplementedError` naming the missing purge, rather than silently under-purging. Writing a full combinatorial purged CV now would be speculative machinery for a horizon nothing emits yet (ponytail); silently accepting the parameter would be a leaky backtest, which is the one failure ADR-012 exists to prevent. (Round 1 note: "drops into existing tooling" — no tooling in this repo currently consumes a sklearn splitter object; the claim is dropped as unearned. The reason to match the splitter protocol is simply that it is the shape `TimeSeriesSplit` itself already has, so wrapping it is a thin decorator, not a new protocol.)

**`min_train_size` (decision 3) also bounds what configurations are legal.** Measured: `TimeSeriesSplit(n_splits=4, gap=2)` on 10 points raises `ValueError: Too many splits...for number of samples` **before yielding a single fold** — there is no fold set to filter in this case, only total infeasibility. `PurgedWalkForward.split()` lets that propagate as-is; `gate.py` catches it and reports `GateVerdict(status="INVALID", reasons=["infeasible_split_configuration"])` directly, distinct from and reached before decision 3b's per-fold path (round 3 H7 — round 1's M7 fix had conflated the two, recording this in `GateVerdict.skipped` in one place and as a direct run-level verdict in another; it is only ever the latter, since a `ValueError` here means the splitter produced zero folds, not some folds worth recording individually).

Emitting the *combinatorial* variant (CPCV) is out of scope and named in Out of Scope.

### 6. Fee schedule: the numbers in issue #6 are stale — verified rates below

Issue #6 specifies "STT: 0.1% sell equity, stamp: 0.015%, GST: 18% on brokerage, exchange: 0.00345%". Verified 2026-08-14 against the published broker schedule; four of those are wrong or incomplete:

| Charge | Issue #6 | Verified | Side |
|---|---|---|---|
| STT equity delivery | 0.1% sell | **0.1% buy *and* sell** | both |
| STT equity intraday | — | 0.025% | sell |
| STT equity futures | — | **0.05%** | sell |
| STT equity options | — | **0.15% on premium** (+0.15% intrinsic on exercise) | sell |
| Exchange txn (NSE equity) | 0.00345% | **0.00307%** | both |
| Exchange txn (NSE futures) | — | 0.00183% | both |
| Exchange txn (NSE options) | — | 0.03553% on premium | both |
| SEBI turnover | — | ₹10/crore = 0.0001% | both |
| Stamp duty (delivery) | 0.015% | 0.015% | **buy only** |
| Stamp duty (intraday / fut / opt) | — | 0.003% / 0.002% / 0.003% | buy only |
| GST | 18% on brokerage | **18% on (brokerage + SEBI + exchange)** | both |

**Also missing entirely from the issue: DP charges** — a *flat* ~₹15.34 per scrip per day on delivery sells (₹3.5 CDSL + ₹9.5 broker + ₹2.34 GST — **the GST component is baked into this constant, not computed by our schedule**, source: broker charges page, verified 2026-08-14), independent of notional. On a ₹10,000 delivery round trip that single flat fee is ~0.15%, larger than every percentage charge combined. Omitting it makes small-notional delivery strategies look profitable when they are not, which is exactly the Layer 3 failure mode ADR-011 warns about ("strategies profitable pre-cost are routinely negative post-cost").

**A flat charge and a percentage schedule are both meaningless without something to price them against — round 1's B1 — and round 2 (B6) caught that the first fix under-specified it: a scalar can't hold "one value per observation", and notional alone can't tell a flat per-sell charge from a percentage per-trade charge.** `EvalRequest` gains three fields, all length-matched to `returns`:

- `position_notional: Sequence[Annotated[float, Field(allow_inf_nan=False)]]` (round 13 H24 — this line still declared the pre-round-12 `Sequence[float]` form; H22's `allow_inf_nan=False` fix touched decision 7b's field table but missed this second, earlier declaration of the same field) — ₹ notional at each period (Story #9's caller derives this from position sizing, out of scope here). A `Sequence` typed and validated against `len(returns)` in `types.py`, not a bare scalar — the round-1 wording ("one value per return observation") described this shape but the field itself was declared as a scalar `float`, a contradiction round 2 caught as a hard `mypy --strict` failure at first use.

**`position_notional`'s meaning for `EQUITY_OPTIONS`, pinned (round 13 H28 — a real ambiguity, not previously stated).** Decision 6's fee table charges STT, exchange, and DP on **premium** for options, while every other segment charges on the underlying trade's notional value. "₹ notional at each period" as written does not say which quantity an options entry carries — premium and underlying notional differ by one to two orders of magnitude, and the choice changes the fee (and therefore decision 7's cost-adjusted return) by the same factor. **Decision: for `segment == EQUITY_OPTIONS`, `position_notional[i]` is the **premium** value, matching what the fee schedule actually taxes** — the caller (Story #9) is responsible for passing premium, not underlying notional, for options rows. Verified against the live schedule (decision 6): options STT (0.15%), options exchange (0.03553%), and DP are the *only* charges that key off premium rather than trade notional, so aligning the field to "whatever `total_fee()` actually multiplies by" is a single consistent rule across all four segments, not a per-segment special case — `total_fee()` never needs to know which quantity it received, only that it is the base the schedule prices against.
- `trade_side: Sequence[Literal["buy", "sell", "hold"]]` — what happened at each period. Required because the fee model in decision 6's own table is asymmetric by side (stamp duty buy-only, STT sell-weighted) and the flat DP charge fires **once per delivery sell, not once per bar held** — without a side/hold signal, `fees.py` cannot distinguish "notional carried forward, no new charge" from "position sold, DP charge applies," and the small-notional-DP-dominates worked example this decision is built around is not computable from notional alone. A `hold` period contributes zero fees regardless of notional.
- `capital: Annotated[float, Field(gt=0.0, allow_inf_nan=False)]` — starting capital, scalar (one value for the whole run, not per-period), used as the Sortino return base in decision 7. **Round 9 (H12): `capital` is a divisor in decision 7's formula and was declared as a bare `float` with no bound — `calls` and `position_notional` were bounded at exactly this kind of edge in decisions 4 and L4, but the field that is actually divided into every period return was left open.** Measured: an unbounded `capital` accepts `0.0` (`ZeroDivisionError` at the first Sortino computation) and negative values — `capital=-1_000_000` on decision 7's own worked example silently **sign-flips every period return**, so a losing strategy scores as a winner without raising anything. `Field(gt=0.0)` verified to reject both `0.0` and negative values under Pydantic while accepting any positive float. **`allow_inf_nan=False` added (round 13 H25) — `gt=0.0` alone accepts `inf` (`inf > 0.0` is `True`), and `capital=inf` reproduces H22's own failure shape one field over: on decision 7's own fixture, `capital=inf` collapses every `period_returns[i]` to `0.0`/`-0.0`, giving zero downside deviation and `LayerScore.value=None, note="no_downside_observations"` for a run that actually had losses — a plausible, silently wrong result rather than an error.** This is why H22's Sequence-shaped sweep (`returns`/`forecasts`/`position_notional`) was incomplete: `capital` is the fourth unguarded numeric field, but scalar, not a `Sequence`, so it needed the same fix stated separately rather than assumed covered by the sweep.

Percentage fees apply to `position_notional[i]` on periods where `trade_side[i] != "hold"`; the flat DP charge applies once per period where `trade_side[i] == "sell"` **and** `segment == EQUITY_DELIVERY`, independent of `position_notional[i]`'s magnitude — which is precisely why it dominates at small size and is exactly the case decision 6 exists to catch.

**`trade_side` coherence, and its one known limitation (round 3 M12).** `types.py` validates two structural constraints: a `"sell"` or `"buy"` period requires `position_notional[i] > 0` (round 4 L4 — a bare "non-zero" check would accept a negative notional, which is not a meaningful trade size; a sell or buy of nothing, or of a negative amount, is malformed input either way), and consecutive `"hold"` periods require the notional to be non-increasing only by construction of the caller — this package does not track position state across periods, so it cannot detect "a hold reporting more notional than was ever bought." That is a caller invariant (Story #9), stated here as a boundary this package does not enforce, not silently assumed.

**Known, accepted limitation: fold boundaries can split a trade.** A `"sell"` in a test fold whose matching `"buy"` fell in the training fold is scored on that test fold as if the position appeared from nothing — the sell's fee and its return are both real and both belong in that fold's ledger, but the entry cost was incurred outside the walk-forward window being scored. This is a property of walk-forward evaluation applied to a stateful strategy, not a bug specific to this design: any purged CV scheme evaluating a multi-period position has the same edge at fold boundaries. Out of scope to solve here (it would require fold-aware position reconstruction, which is Story #9/#6-M7 territory once a real strategy exists to reconstruct); recorded so it isn't rediscovered as a surprise during implementation.

**Decisions:**
- `IndianFeeSchedule` is a frozen dataclass with **per-segment profiles** (`EQUITY_DELIVERY`, `EQUITY_INTRADAY`, `EQUITY_FUTURES`, `EQUITY_OPTIONS`), each carrying buy-side and sell-side rates separately. A single symmetric rate cannot express buy-only stamp duty or sell-only STT.
- Fees model **both percentage and flat components**, applied to `position_notional`. A schedule that only multiplies by notional is structurally unable to represent DP charges.
- **The DP flat charge is excluded from the GST base** — it is already GST-inclusive per the source breakdown above, and applying the schedule's own 18% on top would double-count a tax already paid. GST applies only to (brokerage + SEBI turnover + exchange transaction charges), per the verified table.
- Rates carry an `effective_from` date and the schedule is **selected by trade date**, not by "now". A 2023 backtest priced at 2026 STT rates is a wrong number that looks right. This is cheap now and a data migration later.
- Brokerage is a constructor parameter defaulting to zero (discount-broker delivery). GST then correctly computes as 18% of (0 + SEBI + exchange) rather than silently vanishing.
- Rates live in `fees.py` as literals with **the source URL and verification date in the fees module docstring** (mirrored here for review, since a docstring alone isn't reviewable in a diff-only read: broker charges page, verified 2026-08-14). They change once or twice a year and a wrong rate must show up in a code diff and a test, not in a config file nobody reviews.

### 7. Sortino: downside deviation with a **zero** MAR, annualized by fold length, and it raises on zero downside

**The cost adjustment, stated explicitly (round 2 B6 asked for this; round 3 B9 found decision 7 still hadn't defined it).** `fees.py`'s `IndianFeeSchedule.total_fee(position_notional_i, trade_side_i, segment, timestamps_i)` returns a ₹ amount for period *i* (decision 6). **Round 10 H15 — the signature was missing the trade date entirely**, contradicting decision 6's own `effective_from`-based rate selection and the Testing section's pre-2024-trade-date test; `timestamps_i` (already a field on `EvalRequest`, decision 7b) is the date `total_fee()` selects the correct rate vintage against — no new field needed, only the missing parameter in this signature. The **cost-adjusted per-period return** feeding Sortino is:

```
period_returns[i] = returns[i] * position_notional[i] / capital - total_fee(position_notional[i], trade_side[i], segment, timestamps[i]) / capital
```

(Round 11 H19: the three-argument form above is what H15's own fix, three lines earlier in this same decision, was raised to remove — a call site not updated when its own signature was. `timestamps[i]` is the trade date `total_fee()` selects the rate vintage against, per decision 6's `effective_from` and H15's fix to `total_fee()`'s signature.)

**Round 4 (B10) found the round-3 formula dimensionally wrong, and wrong in exactly the direction that erases decision 6's headline finding.** The round-3 version asserted `returns[i]` is "itself a return on `capital`" — false everywhere else in this spec: decision 1 calls `returns` a "300-point Gaussian return series … daily returns" and "already differenced prices", it is the MASE target, and decision 7b derives the Brier label from `returns[i] > 0.0` — market direction, not portfolio P&L. `returns[i]` is an **asset** return, a return on `position_notional[i]`, not on `capital`. Measured on the worked example (`capital=1,000,000`, `position_notional=10,000`, `returns[i]=0.01`, DP=₹15.34):

```
round-3 formula:  0.01 - 15.34/1_000_000        = 0.00998466   (fee drag ≈ 0.15% of the return)
corrected formula: 0.01*10_000/1_000_000 - 15.34/1_000_000 = 0.00008466  (fee drag ≈ 15.3% of the return)
```

The round-3 formula understated the fee's drag by exactly `capital/position_notional` (100× here), making the DP charge look negligible in precisely the small-notional regime decision 6 exists to expose — the opposite of its stated purpose. **`returns[i]` is exposure-weighted by `position_notional[i]/capital` before the capital-denominated fee is subtracted**, so both terms share the same base (a return on total capital) and the equation is dimensionally consistent.

**Round 15 (inline) — a precondition this dimensional-consistency argument depends on, made explicit for the first time: `returns[i]` and `position_notional[i]` must be returns and notional *on the same underlying quantity*, for every segment, not only for the delivery/intraday/futures cases where "the trade's notional" is unambiguous.** For `EQUITY_OPTIONS`, decision 6's H28 fix pins `position_notional[i]` to **premium** (matching what the fee schedule taxes). `returns[i] * position_notional[i] / capital` is dimensionally sound *only if* `returns[i]` is also a return on premium — an option's return on the *underlying's* price movement is a different, generally much larger number (options are leveraged), and multiplying a premium-return-scale × position_notional-as-premium is correct while multiplying an underlying-return-scale × premium is not. **This spec does not construct `returns[i]`** — it is supplied by `EvalRequest` (Story #9's caller) — so the fix is a stated caller contract, not new code here: **`returns[i]` must be a return on whatever quantity `position_notional[i]` represents for that segment** (trade notional for delivery/intraday/futures, premium for options). This generalizes cleanly rather than special-casing options, and is recorded as an explicit `EvalRequest` invariant this package assumes and does not itself validate — validating it would require re-deriving `returns[i]` from prices this package doesn't receive (decision 6's own `prices` field was cut as unused, M15), which is out of scope here and belongs with whatever constructs the request.

**The `hold` case, stated explicitly (round 4 asked this not be left implicit):** on a `hold` period, `trade_side[i]=="hold"` means no new fee (`fee=0`), but if `position_notional[i]` is nonzero — a position carried forward from an earlier period — the return is **still** exposure-weighted: `period_returns[i] = returns[i] * position_notional[i] / capital`. Dropping the exposure weighting on hold periods would mean a strategy that is *flat* (`position_notional=0`) during a market downturn silently absorbs the market's loss into its own Sortino score — measured: unweighted gives `−0.05` on a −5% day with zero exposure, exposure-weighted correctly gives `−0.0`. A flat strategy has no downside exposure to score.

Target return (MAR) = 0, not the risk-free rate: the deficiency being measured is loss, and mixing in a T-bill rate makes the number depend on a rate curve we do not ingest. Downside deviation divides by **N**, not by the count of negative observations — dividing by the negative count is a common implementation that rewards a strategy for having few, huge losses.

Zero downside deviation (no losing period in the fold) → `sortino = inf` is mathematically correct and operationally useless. **Decision: `LayerScore.value = None` with `LayerScore.note = "no_downside_observations"`** (decision 7b's field, not a `GateVerdict` reason — this is a per-layer result annotation, not a gate failure). A fold with no losses is a sample-size statement, not an infinitely good strategy, and `inf` propagates into any mean.

Annualization uses 252 trading days as a named module constant, applied only when the fold covers ≥ 20 observations; below that the raw per-period figure is reported with `annualized=False`. **`20` is a judgment call, stated as one (round 9 L7) — the same treatment `min_train_size=3`'s default received under review pressure.** "Annualizing a 5-day fold produces a headline number with no meaning" argues against a threshold as low as 5, not for exactly 20; there is no derivation for the specific number, only the direction. `20` is chosen as roughly one trading month — enough periods that a `√252` scale-up is not dominated by one or two outlier days — and is a named module constant precisely so it can be revised against real fold-size distributions during implementation without being mistaken for a derived requirement.

**Formula, stated exactly (round 1 H5 — three equivalent-looking readings were left ambiguous):** `sortino_annualized = (mean(period_returns) * 252) / (downside_deviation(period_returns) * sqrt(252))` — annualize the numerator by the trading-day count and the denominator by its square root, matching the standard Sharpe/Sortino annualization convention (return scales linearly with time, volatility with its square root). Verified numerically equivalent to scaling the raw per-period ratio by a bare `sqrt(252)` (measured: `9.63991701` both ways) — the spec picks the numerator/denominator form because it is the one that generalizes if the annualization factor ever differs between return and risk (it does not here, but the equivalence is a property of `252`, not of the formula, and should not be relied on if that constant ever changes per-segment).

### 7b. `types.py` field types, stated (round 1 H3, still open through round 2 — closed here)

`EvalRequest` (all `Sequence`-typed fields length-matched to `returns`, validated in a Pydantic `model_validator(mode="after")` that raises `ValueError(f"length mismatch against returns (n={n}): {mismatched}")` naming every offending field and its actual length in one message, not just the first — round 11 M24: prior rounds named the mechanism but never its error contract or a regression test; verified the pattern raises `pydantic.ValidationError` wrapping that `ValueError`, and the Testing section's `EvalRequest` fixtures now include a length-mismatch case distinct from the existing missing-field case, which exercises a different Pydantic code path): `returns: Sequence[Annotated[float, Field(allow_inf_nan=False)]]`, `forecasts: Sequence[Annotated[float, Field(allow_inf_nan=False)]]`, `calls: Sequence[Annotated[float, Field(ge=0.0, le=1.0)]]` (probability of the bull outcome — round 3 L3: the bound must be on `Annotated[float, Field(...)]` wrapping each element, not a bare `Field(...)` at the field level, which constrains the sequence rather than its items; verified `[0.5, 1.4]` raises `less_than_equal` under the `Annotated` form. This is also decision 4's fix for round 2's M10, since the bound rejects an out-of-range confidence before it ever reaches `np.digitize`, rather than relying on `digitize` to clip silently), `timestamps: Sequence[AwareDatetime]` (round 13 M26 — `Sequence[datetime]` does not enforce timezone-awareness; a bare `datetime` accepts naive values, and a request mixing naive and aware timestamps makes the gate's own `max(timestamps) <= as_of` comparison raise an unhandled `TypeError` — `AwareDatetime`, Pydantic's dedicated type, rejects naive values at construction, verified), `as_of: AwareDatetime`, `segment: Literal["EQUITY_DELIVERY", "EQUITY_INTRADAY", "EQUITY_FUTURES", "EQUITY_OPTIONS"]`, `position_notional: Sequence[Annotated[float, Field(allow_inf_nan=False)]]`, `trade_side: Sequence[Literal["buy", "sell", "hold"]]`, `capital: Annotated[float, Field(gt=0.0, allow_inf_nan=False)]` (round 9 H12 — a divisor field, bounded to strictly positive to prevent a zero or negative value from producing a `ZeroDivisionError` or a silently sign-flipped result; see decision 6's field-by-field detail).

**`allow_inf_nan=False` on `returns`/`forecasts`/`position_notional` (round 12 H22 — a real gap, not a defensive nicety).** Measured: bare `Sequence[float]` accepts `[nan, inf, 1.0]` without error, and `nan`/`inf` then propagate *past* decision 3's degeneracy gate — the gate inspects only the training-fold baseline, not every element, so a `nan` sitting in a test fold sails through a passing gate. Two concrete failure shapes measured: MASE on a `nan`-containing fold returns `nan`, a `float`, not `None`, so H14's not-`None` exclusion rule never catches it and it silently corrupts `layer_means[1]`; Brier is worse — `nan > 0.0` evaluates `False`, so a `nan` return is silently labeled not-bull and `brier_score_loss` returns a clean, plausible-looking `0.25` from corrupt input, with no error anywhere in the chain. `calls` was already implicitly protected (`ge=0.0, le=1.0` rejects `nan`/`inf` under Pydantic's own float validator, verified), which is exactly why this gap on the other three sequence fields is an inconsistency at the same trust boundary decision 4/H12 already bounded, not a new category of concern.

**`prices` cut from `EvalRequest` (round 4 M15).** No module in this design consumes raw prices — MASE, Brier, and Sortino all operate on `returns` (decision 1's "already differenced prices" framing means the differencing already happened upstream, in whatever produces `EvalRequest`). A field with no reader is dead weight in a Pydantic model under `mypy --strict`, and ponytail cuts it rather than carrying it speculatively for a future consumer that doesn't exist yet.

**Brier label, stated (round 1 H3's other half):** the observed binary outcome is `1 if returns[i] > 0.0 else 0`. A period with `returns[i] == 0.0` is labeled `0` (not-bull) rather than dropped or split — a zero-return period did not confirm the bull call, and dropping it would let a model dodge scoring by predicting into flat periods. This is a judgment call, recorded as such: `calls[i]` is the model's stated P(bull), independent of how the label is derived, so the derivation rule is this spec's decision, not a data-flow inevitability. **Consistency with decision 1/2's MASE, checked explicitly:** MASE never classifies a period, it only measures forecast error against the naive/zero baselines — there is no competing "flat means X" rule in Layer 1 for this one to contradict. The two layers score different things (forecast error vs. calibrated confidence) from the same `returns` array without needing to agree on a shared definition of "flat."

**Remaining Pydantic models, field-typed (closes round 1/2/3's open half of H3):**
- `Fold`: `train_idx: Sequence[int]`, `test_idx: Sequence[int]`, `fold_number: int`. **`fold_number`'s numbering rule, pinned (round 11 H21 — unstated across 10 prior rounds; every join across `GateVerdict.folds`, `GateVerdict.skipped`, and `LayerScore` depends on this key meaning one thing):** `fold_number` is the **0-based index in `PurgedWalkForward.split()`'s own emission order**, assigned once, before any per-fold filtering (decision 3's `min_train_size`/degeneracy checks) runs — never renumbered among survivors. Measured collision this rule prevents: on `n=20, n_splits=5, gap=4, min_train_size=3`, `split()` emits 5 folds, fold `0` (size 1) is skipped, folds `1-4` survive; **renumbering survivors from 0** would make the first surviving `Fold.fold_number` collide with the skipped `FoldSkipReason.fold_number=0` inside the same `EvalResult`, two different folds sharing one identifier. Emission-order numbering keeps the identifier unique and stable across the whole result regardless of how many folds are skipped.
- `FoldSkipReason`: `fold_number: int`, `reason: Literal["degenerate_baseline", "below_min_train_size"]`, `detail: str` — **format pinned (round 11 L12, previously "human-readable" with no assertable content):** for `reason="below_min_train_size"`, exactly `f"train size {n} < min_train_size {min_train_size}"`; for `reason="degenerate_baseline"`, exactly `f"mean(|Δy_train|) = {value}"` where `value` is `"nan"`, `"inf"`, or `"0.0"` per whichever arm fired (decision 3 — round 13 M27 corrected the token set from two to three: the `isfinite` arm also fires on float overflow, measured with `train=[-1e308, 1e308, -1e308]` yielding `mean=inf`, a case the original two-token enumeration didn't admit). Both are machine-parseable (a test can regex-extract the two integers or the value token) rather than merely eyeballable, and pinned exactly rather than left to whatever the implementer's first draft happens to produce. Scoped to exactly the two per-fold causes decision 3/3b's B8 fix routes through `gate.py` — `infeasible_split_configuration` (decision 5) is a run-level `GateVerdict` reason, never a `FoldSkipReason`, per H7's fix above; the two enums do not overlap. **Precedence, stated (round 4 M13):** a 1-element fold trips both `below_min_train_size` (its length) and `degenerate_baseline` (its `mean(|Δy|)` is `nan`) simultaneously. `gate.py` checks `below_min_train_size` first and records that reason if it fires — it requires only a length comparison, not computing the baseline at all, so a fold that fails it is rejected before the baseline computation that `degenerate_baseline` depends on ever runs. `degenerate_baseline` is therefore only reachable for folds that already cleared the size floor.
- `CalibrationBin` (round 4 B11, new model — `LayerScore.metadata` as a `dict[str, float]` couldn't hold what decisions 4 and 7 promised it would): `count: int`, `mean_predicted: float`, `mean_observed: float`. One instance per calibration bin (decision 4's all-10-bins-including-empty promise).
- `LayerScore`: `layer: Literal[1, 2, 3]`, `fold_number: int`, `value: float | None` (nullable — decision 7's no-downside-observations case), `calibration_bins: Sequence[CalibrationBin] | None` (populated only for Layer 2, decision 4's bin table), `note: str | None` (carries decision 7's `"no_downside_observations"`, or other layer-specific flags as free text — round 4 B11: the round-1 `metadata: dict[str, float]` field is dropped because it is a `float`-valued dict and cannot hold a bin table or a string reason; a typed field per actual payload replaces the untyped catch-all), `zero_forecast_mase: float | None` (decision 2, populated only for Layer 1), `beats_zero: bool | None` (decision 2, populated only for Layer 1), `annualized: bool | None` (decision 7, populated only for Layer 3). Each of the last three is populated for exactly one `layer` value and `None` for the other two — a per-layer union type would encode that exhaustively but is unwarranted machinery for three optional fields on one model; the constraint is documented here, not enforced by the type system.
- `GateVerdict`: `status: Literal["VALID", "INVALID"]`, `reasons: Sequence[str]` (empty when `VALID`), `folds: Sequence[Fold]`, `skipped: Sequence[FoldSkipReason]`. **Membership contract, pinned (round 12 H23 — round 11's H21 fix pinned `fold_number`'s numbering but not this; the round-11 recommendation itself named the missing clause and it didn't make it into the applied fix):** `folds` holds **survivors only** — every fold that cleared decision 3's per-fold checks and was handed to L1–L3. `folds` and `skipped` are disjoint by `fold_number`, unconditionally. **The union clause is scoped, not unconditional (round 13 H26 — stated unconditionally, it was false on the `infeasible_split_configuration` path decision 5 itself defines):** whenever the splitter emits at least one fold, `folds`'s and `skipped`'s `fold_number` sets union to exactly `range(n_splits)`, decision 5's emission count. On the `infeasible_split_configuration` path (`TimeSeriesSplit` raises on its first `next()` — measured, `n=10, n_splits=4, gap=2` — before yielding any fold at all), `folds = []` and `skipped = []` both, and `n_splits` is not the emission count on that path since the splitter never got that far; the union claim does not apply there, matching decision 5's and the Walk-forward test bullet's existing "`skipped` never populated" requirement for that path. Every `LayerScore.fold_number` across `layers` is guaranteed present in `folds` (never in `skipped`), unconditionally — since `LayerScore` is only produced for folds L1–L3 actually ran on, which is exactly the survivor set, empty or not. A downstream consumer (Story #9) can therefore join `LayerScore.fold_number` against `GateVerdict.folds` and never miss.
- `LayerMean` (round 10 H17, new model — a bare `float` can't carry how many folds it was averaged over): `mean: float`, `n_folds: int`.
- `EvalResult`: `verdict: GateVerdict`, `layers: Sequence[LayerScore]`, `layer_means: dict[Literal[1, 2, 3], LayerMean]` (round 9 H14, revised round 10 H17 — see below). **`invalid_folds` cut (round 4 M14):** it duplicated `GateVerdict.skipped` with nothing keeping the two in sync — a caller who wants the skipped-fold summary reads `result.verdict.skipped` directly, since `EvalResult.verdict` already is a `GateVerdict`. Every earlier reference to `EvalResult.invalid_folds` in this document (Data Flow diagram, decisions 3b/5, Testing section) refers to `result.verdict.skipped` instead.

**"Aggregated" defined (round 9 H14 — Data Flow, decision 3, decision 3b's `< 2` floor, and decision 7's `None`-not-`inf` case all justify themselves by an aggregate that no prior round ever gave a field or a formula, leaving the word doing structural work in four different arguments without a referent).** `EvalResult.layer_means[layer]` is the mean of that layer's per-fold `LayerScore.value` **over folds where that layer's value is not `None`** — a Layer-3 fold with `no_downside_observations` (decision 7) contributes to Layer 1's and Layer 2's means but is excluded from Layer 3's, since including a `None` as `0.0` would silently reward the exact ambiguity decision 7 introduced `None` to avoid propagating.

**Round 10 (H17) found decision 3b's `< 2` gate-valid-fold floor does not actually protect this mean's meaningfulness, contrary to this paragraph's own original closing claim.** The floor counts gate-valid folds (a property of `returns` alone, checked layer-agnostically before L1–L3 run); `layer_means[3]` counts only the subset of those folds with a non-`None` Layer-3 value. Measured: 5 gate-valid folds where 4 have `no_downside_observations` (a flat fold — all-zero period returns → zero downside deviation → `None`, decision 7) still passes decision 3b's floor (5 ≥ 2) and produces `layer_means[3]` computed over exactly **1** fold — a single-fold value read by a downstream consumer as if it were a walk-forward aggregate.

**Fix (recommendation (a) from round 10, applied): `layer_means[layer]` is a `LayerMean{mean, n_folds}`, not a bare `float`, and is populated only when `n_folds >= 2` for *that specific layer* — a second, per-layer floor, independent of decision 3b's request-level floor.** A layer with fewer than 2 contributing folds reports no entry in `layer_means` (a caller checks `layer in result.layer_means`) — the same "missing means insufficient data, not zero" convention decision 3b already established at the request level (round 11 M23: an earlier draft of this sentence claimed this membership-check pattern was "already used elsewhere in this document" — grepped, it is not; the convention is justified on its own terms, by decision 3b, not by a nonexistent precedent), this extends it to the per-layer level since decision 3b's floor alone was shown insufficient. `n_folds` lets any consumer that reads a present entry also see how much data backs it, rather than a mean and a count silently diverging across `Layer 1`/`2` (which typically have `n_folds` close to the gate-valid count) and `Layer 3` (which can be much lower).

### 9. Pure functions, and what "pure" costs

Every metric is a module-level function: arrays in, floats out, no I/O, no logging, no clock. `evaluate()` composes them. Consequences accepted: the caller assembles `EvalRequest` (Story #9's job), and there is no incremental/streaming evaluation — a re-score recomputes everything. At our data sizes (thousands of daily bars) that is milliseconds, and the property this buys — the same inputs always produce the same score, forever, so eval history stays comparable across runs — is the whole point of ADR-012.

No `random_state` anywhere. Nothing in the pipeline samples.

**`evaluate()`'s actual signature, stated (round 9 H11 — every earlier round wrote `EvalRequest` as if it were the sole input, but `horizon` (decision 5, load-bearing for the `gap >= horizon` leakage guarantee), `min_train_size` (decision 3, default `3`), `n_splits`, and `gap` are all splitter configuration that decision 5/9 require and that `EvalRequest`'s field table never carries — an omission, not a design choice, since nothing in Scope or Decisions argues they belong on the request object):**

```python
def evaluate(
    request: EvalRequest,
    *,
    horizon: int = 1,
    min_train_size: int = 3,
    n_splits: int = 5,
    gap: int | None = None,  # sentinel; resolved to `horizon` in the function body below
) -> EvalResult:
    effective_gap = horizon if gap is None else gap
    # ... construct PurgedWalkForward(n_splits=n_splits, gap=effective_gap, horizon=horizon, min_train_size=min_train_size) and proceed
```

**Round 10 (M18) confirmed the resolution step was a comment, not code — `gap: int | None = None` cannot default to `horizon`'s value directly, since Python evaluates parameter defaults at function-definition time, before any call supplies a value for `horizon`.** No default expression can reference a sibling parameter; `None` is a sentinel resolved in the body, which the signature above now shows explicitly (`effective_gap = horizon if gap is None else gap`) rather than leaving to an inline comment a reader could take as the actual mechanism.

**Bounds on `min_train_size`/`n_splits`/`horizon` (round 12 M25 — plain `int` parameters were unbounded).** `PurgedWalkForward.__init__` validates `min_train_size >= 3`, `n_splits >= 2`, and `horizon >= 1`, raising `ValueError` with the offending parameter and value if violated — **enforced at the splitter's own construction (round 13 M28, superseding round 12's placement in `evaluate()`), not just at the one call path that happens to go through `evaluate()`.** Round 12's original fix put these checks in `evaluate()` alone while `gap >= horizon` and the `horizon > 1` `NotImplementedError` (decision 5) were already asserted *by the splitter itself* — one parameter set enforced in two different places was decision 8's "does not trust its own callers by convention alone" violated by omission, since the Testing section's Walk-forward bullets construct `PurgedWalkForward` directly (a white-box test of an internal, not through `evaluate()`), and that path was unbounded. Moving all four checks into the constructor means `evaluate()` inherits them by construction (it still surfaces the same `ValueError` to its own caller) and the direct-construction test path is bounded identically — one enforcement point, not two. **The floor is `3`, not `2` (round 13 H27 — the round-12 fix's own arithmetic was wrong: a size-2 train array yields exactly 1 diff, measured, not "fewer than 2 diffs" as claimed, so a floor of `2` does not in fact guarantee more than one diff to average).** Decision 3's default of `3` and this floor now coincide — the floor is no longer weaker than the default it's supposed to bound, closing the actual gap: at `min_train_size >= 3`, the minimum possible diff count is `2`, and no caller override — direct or through `evaluate()` — can push a fold down to a single-diff baseline.

**Round 13 M27, resolved as a consequence of the above, plus one case the constructor floor alone doesn't reach:** with the floor now enforced at construction, `mase.py`'s `isfinite`/`==0.0` defense-in-depth guard's `nan` arm (decision 3, originally motivated by a 1-element train fold) is unreachable through any `PurgedWalkForward`-mediated path — every fold the splitter can produce now has ≥2 diffs. The arm is **not** dead code, though: finite elements can still produce a non-finite *mean* by float overflow — measured, `train=[-1e308, 1e308, -1e308]` passes `allow_inf_nan=False` element-wise (each value is finite) and yields `mean(|Δy|) = inf`. `FoldSkipReason.detail`'s pinned token set (decision 7b) is corrected from `{"nan", "0.0"}` to `{"nan", "inf", "0.0"}` to admit this case; the `nan` token itself is retained in the set as a defense-in-depth guarantee for any future caller that constructs `Fold` objects bypassing `PurgedWalkForward` entirely, even though the constructor floor makes it unreachable via the documented entry points.

**Why splitter configuration is a call parameter and not an `EvalRequest` field:** `EvalRequest` is *data* — what happened, priced and timestamped. `horizon`/`min_train_size`/`n_splits`/`gap` are *evaluation methodology* — how that data is partitioned and scored, which can legitimately vary across two calls scoring the identical request (a walk-forward sensitivity sweep re-evaluates the same `EvalRequest` at several `n_splits` values without re-fetching or re-validating the data). Folding them into `EvalRequest` would make the request mutable-by-methodology and complicate the "same inputs, same score" guarantee this decision opens with, since two evaluators would need to construct two different `EvalRequest` objects for what is genuinely the same underlying data. `gap` defaults to `horizon` — decision 5's stated minimum for the embargo to be equivalent to purging — rather than to `TimeSeriesSplit`'s own default of `0`, so an un-overridden call does not silently under-purge.

## SOLID / Clean Architecture

**SRP** — one metric per module; `fees.py` owns fee computation exclusively (rate selection, side/segment lookup, GST base — round 9 M16 corrected the earlier "data, no logic" framing, since `total_fee()` is real logic, just logic scoped to one responsibility: pricing a single period's charge); `gate.py` decides, `walk_forward.py` splits. **DIP** — the pipeline takes an `EvalRequest`, never a data client; nothing in `evaluation/` imports from `data_server/` or the harness, so the dependency rule holds by construction (enforced by a test asserting the package's import closure contains no first-party module outside `evaluation`). **OCP** — a fifth metric layer is a new module plus a line in `pipeline.py`; adding a market segment is a new `FeeProfile` literal. **ISP** — no interface here is wide enough to violate; there is deliberately no `Metric` ABC, because three functions with different signatures forced behind one interface would be an abstraction serving nobody. **Composition** — the pipeline composes functions; the only inheritance is `DegenerateBaselineError`'s from `Exception` and every Pydantic model's from `BaseModel` (round 11 M22 — "the error hierarchy" was stale after `EvaluationError`'s cut, round 9 L5, left this package with exactly one exception, not a hierarchy).

Deliberate departure from the project's OOP-throughout rule, stated rather than smuggled: metrics are functions, not classes, because they hold no state and a class wrapping one pure function is a namespace with extra steps. `PurgedWalkForward` *is* a class because it holds split configuration and implements sklearn's splitter protocol.
